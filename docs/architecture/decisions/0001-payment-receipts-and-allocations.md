# ADR-0001: Разделить факт поступления денег и распределение по начислениям

- **Статус:** Accepted.
- **Дата:** 2026-11-06.
- **Область:** ручные и подтверждённые платежи арендатора, распределение аванса,
  contract timeline и текущие API/ledger-проекции.

## Контекст

Сейчас `payments` одновременно означает деньги, полученные от арендатора, и их
распределение по `rent_charges`. `LedgerService` вычисляет `total_paid` как сумму
всех строк `PaymentModel`, включая авансы, а баланс — как `Σcharges − Σpayments`.
Схема не хранит самостоятельный receipt ID или связь между строками, возникшими
из одного поступления.

`PaymentService._auto_distribute` и `_create_linked_payment` создают split-строки,
после чего записывают одно событие на полную сумму запроса. В
`event_metadata.payment_id` попадает только ID первой созданной строки.
`ContractEventModel` хранит этот ID как JSON string: внешнего ключа на `payments`
нет. Событие не содержит ссылки на остальные split-строки.

`allocate_unlinked_payments` блокирует договор, затем начисления и авансы,
создаёт новые linked payment rows, а полностью использованный исходный advance
удаляет. Для частичного распределения исходная строка обновляется. Отдельное
событие распределения не создаётся. `update_payment` меняет сумму и остальные
поля строки, `delete_payment` удаляет строку; ни одна операция не добавляет
событие корректировки. Вызовы сервиса сериализуются блокировкой договора, но это
не сохраняет прежнее состояние строк.

Идемпотентность запроса для `POST /v1/payments` решает повтор бизнес-эффекта по
одному ключу в течение 24 часов. Его response snapshot не является
идентификатором поступления:
после распределения advance сохранённый ответ может вернуть ID уже удалённой
строки. Без ключа повтор POST остаётся отдельным созданием.

## Characterization evidence

Интеграционный тест
`test_receipt_split_allocation_edit_delete_and_duplicate_history` в
`backend/tests/integration/test_payments_api.py` фиксирует фактические значения
для поступления 1500 при первом начислении 1000 и следующем начислении 500.
`received` ниже означает текущую сумму строк `payments`, которой сейчас
пользуется ledger как суммой поступлений; отдельной исторической суммы receipt
в модели нет.

| Состояние | `Σcharges` | `Σpayments` / received proxy | `Σallocated` | Аванс | Ledger balance | История и ссылки |
|---|---:|---:|---:|---:|---:|---|
| До поступления | 1000 | 0 | 0 | 0 | 1000 | Строк и payment event нет |
| Receipt 1500, charge 1000 | 1000 | 1500 | 1000 | 500 | -500 | Две строки; event amount=1500 ссылается только на linked row 1000 |
| Добавлен charge 500, до allocate | 1500 | 1500 | 1000 | 500 | 0 | Исходный advance ID ещё существует |
| После двух конкурентных allocate | 1500 | 1500 | 1500 | 0 | 0 | Результаты `[1, 0]`; исходный advance удалён, вместо него создана новая linked row без event |
| Replay того же key | 1500 | 1500 | 1500 | 0 | 0 | Новых строк и событий нет; snapshot всё ещё содержит удалённый advance ID |
| Update первой linked row с 1000 до 900 | 1500 | 1400 | 1400 | 0 | 100 | Event amount остаётся 1500, его payment ID теперь указывает на строку 900 |
| Delete первой linked row | 1500 | 500 | 500 | 0 | 1000 | Event остаётся, но его `payment_id` больше не разрешается |

Следовательно, это реальная потеря аудиторской цепочки, а не только отсутствие
таблицы с названием `receipts`: сумма первоначального receipt после split не
связана со всеми его распределениями; allocation может уничтожить исходный ID;
edit/delete меняют или удаляют денежные строки без неизменяемого корректирующего
следа; contract event сохраняет сумму и строковый ID, но после удаления ID не
разрешается. Финансовый ledger остаётся вычислимым по текущим строкам, однако он
не позволяет восстановить первоначальные receipt и все последующие изменения.

## Инварианты

1. Факт поступления имеет стабильный ID и неизменяемые исходные поля: сумма,
   валюта, дата, метод и источник (`manual` или `tenant_claim`). Исправление
   отражается отдельной записью, а не переписыванием исходного факта.
2. Каждое распределение ссылается на поступление и, если оно связано, на
   начисление через неизменяемый снимок цели.
   Сумма активных распределений поступления не превышает его сумму; остаток
   аванса равен `receipt.amount − net allocations`.
3. Перераспределение, исправление и отмена добавляют записи-обращения или
   записи распределения со знаком. Уже записанные факты поступлений и
   распределений не удаляются и не редактируются.
4. Ledger сохраняет денежную семантику: баланс договора равен сумме начислений
   минус net полученные receipts; allocation меняет связь с начислениями, но не
   общую полученную сумму. Депозит остаётся вне ledger.
5. События платежей и история распределений ссылаются на стабильные ключи с
   ограничениями целостности. Область аккаунта, RLS и единая DB-транзакция для
   финансового изменения и его аудита обязательны.
6. Конкурентный allocate не создаёт двойного allocation; повтор POST с тем же
   request key не создаёт второй бизнес-эффект в период хранения ключа. Request
   key не заменяет receipt ID.

## Рассмотренные варианты

### Вариант A — ссылка на поступление и события распределения поверх `payments`

Добавить отдельную неизменяемую запись поступления, `receipt_id` на текущую
проекцию `payments` и дополняемый журнал событий распределения и компенсаций.
Сохранить `payments` как авторитетное текущее представление для ledger и API.

Плюсы: меньшая миграция существующих читателей, API и frontend; проще поэтапная
двойная запись. Минусы: одновременно существуют изменяемая проекция и журнал
событий; каждый путь update/delete/reallocate обязан без исключений писать
события. Аудит зависит от полного и корректного применения журнала, а ledger
по-прежнему нельзя читать как неизменяемую историю.

### Вариант B — отдельные неизменяемые поступления и распределения

Сделать `receipts` источником фактов поступления, а append-only `allocations`
источником распределений и их обращений. Оставить `payments` совместимой
проекцией для текущих API и ledger на период миграции; записи проекции и новые
финансовые факты создавать одной транзакцией. Исправление или удаление в старом
API становится корректирующей записью, а не физическим изменением исторического
receipt/allocation.

Плюсы: cash receipt не смешан с его назначением; сумма поступления и полная
история распределений доступны независимо от проекции; stale ID в timeline
можно устранить FK-ссылкой на стабильный receipt. Минусы: больше таблиц, двойная
запись/проекция, полный охват всех payment write paths и более сложная миграция.

## Принятое решение

Принят **вариант A** как минимальное изменение модели с отдельной неизменяемой
записью поступления и дополняемыми журналами корректировок и распределений.
Текущая `payments` остаётся совместимой проекцией для API и ledger. Для новых записей
`payments.receipt_id` связывает все split-строки с исходным поступлением,
`payments.allocation_event_id` связывает распределённую строку с последним
событием распределения, а `contract_events.payment_receipt_id` даёт временной
шкале стабильную ссылку на поступление. Старый `event_metadata.payment_id`
сохраняется.

`payment_receipts.original_amount` и исходные поля не редактируются. Изменение
суммы или метаданных проекции добавляет `payment_receipt_events`; изменение
суммы allocation сначала компенсирует прежнюю строку, затем добавляет новое
событие. Удаление проекции добавляет отрицательную корректировку суммы и, если
строка была распределена, отрицательное reversal-событие со ссылкой на исходную
allocation. Удаление проекции уменьшает поступление на сумму этой строки;
остальные строки того же receipt сохраняются.

Положительные события `payment_allocation_events` распределяют средства на
начисление; отрицательные `reversal` ссылаются на исходное событие. Цель события
ссылается на `payment_allocation_targets` — неизменяемый снимок начисления.
Поэтому удаление будущего начисления при расторжении договора сохраняется, а
события распределения остаются разрешимыми: сервис добавляет компенсацию и
переносит платёж в аванс. Расчёты продолжают использовать `payments`, поэтому
денежная математика и порядок блокировок не меняются. Поступление и оба журнала
фиксируются в той же транзакции, что проекция и событие договора.

## Данные, миграция и совместимость

- Миграция аддитивна: существующие `payments` и `contract_events` не удаляются
  и не переписываются. Новые tenant-таблицы получают составные account/contract
  FK, RLS, права рабочей роли на чтение/вставку и append-only ограничения.
- Исторические платежи остаются без `receipt_id` и означают `legacy/unknown`.
  Старые группы поступлений, удалённые авансы и прежние значения после edit/delete
  не восстанавливаются: текущие данные этого не доказывают. Backfill финансовой
  истории не выполняется. Снимок начисления создаётся в той же транзакции, что и
  первая новая allocation, даже если само начисление создано до этой миграции.
  Миграция сверяет число и сумму платежей, число contract events и JSON payment
  references до и после DDL.
- Старые contract events и `event_metadata.payment_id` остаются неизменными.
  Для новых событий стабильная FK-ссылка хранится в `payment_receipt_id`.
- HTTP body, стандартные 201 и response schema текущего `POST /v1/payments`, а
  также list/edit/delete контракты сохраняются в период совместимости. Для
  новых API payment IDs должны разрешаться в стабильный receipt или projection
  record. `Idempotency-Key` остаётся необязательной защитой запроса с TTL и не
  используется как идентификатор денежной операции.
- Ручное создание, подтверждение tenant claim, автоматическое и ручное
  распределение, update/delete используют одну транзакционную двойную запись.
  Rollback приложения к старой версии оставляет additive schema на месте; старый
  код создаёт строки `legacy/unknown`, поэтому новые writers нужно восстановить
  до возобновления полного traceability. Downgrade схемы отказывает, пока в
  новых таблицах или FK-полях есть данные. Удаление истории возможно только
  после экспорта и явного разрешения владельца данных.

## Вне этого решения

Не меняются денежная математика и текущий порядок блокировок. YooKassa provider
idempotency, HTTP request idempotency, возвраты/chargebacks и бухгалтерские
проводки не объединяются с receipt/allocation identity; возвраты требуют
отдельного решения.

## Статус утверждения

Вариант A и описанная cutover-семантика приняты владельцем задачи. Schema
migration реализует только новые traceable writes; реконструкция legacy history
остаётся вне этого решения.
