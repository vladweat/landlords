# Частный арендодатель: редизайн лендинга — план реализации

> **Для исполнителей:** использовать обязательный поднавык `superpowers:executing-plans` и выполнять шаги последовательно.

**Цель:** обновить лендинг Landlords для частного арендодателя вокруг контроля платежей и договоров, показывая продукт сразу.

**Архитектура:** оставить страницу отдельным статическим `frontend/public/landing.html`, который nginx отдаёт напрямую. Перестроить разметку и встроенные стили этой страницы; два компактных превью продукта сверстать в том же HTML по реальной структуре dashboard и договоров/платежей без новых зависимостей и пользовательских данных.

**Стек:** HTML, встроенные CSS и JavaScript; существующие React/Vite сборка и nginx-маршрутизация.

**Дизайн:** [`docs/superpowers/specs/2026-10-28-private-landlord-landing-design.md`](../specs/2026-10-28-private-landlord-landing-design.md)

## Общие ограничения

- Основная аудитория — частный арендодатель.
- Основное обещание — платежи и договоры по аренде собраны в одном месте.
- Основной CTA — «Попробовать демо» со ссылкой `#demo`; в блоке `#demo` сохранить текущие публичные данные для входа и кнопку `/login`. Запрос доступа остаётся вторичным.
- Использовать русскую локализацию, светлый фон, зелёный акцент и продуктовый интерфейс в качестве главного визуального элемента.
- Не вводить неподтверждённые обещания, отзывы, клиентские логотипы, статистику использования или реальные данные пользователей.
- Не добавлять зависимости и не менять приложение, API, авторизацию или демо-аккаунт.
- Сохранить работающие ссылки на вход, правовые страницы, контакты и статус.

## Особое внимание при проверке

- Ссылки первого экрана ведут в существующий `/login` и к существующей секции страницы.
- Каждая внутренняя ссылка указывает на существующий ID; навигация не обращается к удалённой секции.
- Дашборд-превью не содержит личных данных или неподтверждённых числовых обещаний.
- На мобильной ширине нет горизонтальной прокрутки; заголовок, CTA и превью читаются в нужном порядке.
- Ссылки на Telegram, email, юридические страницы и `/status` остаются действующими.

### Task 1: перестроить статический лендинг

**Файлы:**
- Изменить: `frontend/public/landing.html`

**Интерфейсы:**
- Сохранить статическую точку входа `/landing.html` и ссылку входа `/login`.
- Сохранить секционные ID `top`, `features`, `how`, `demo`, `faq`, пока на них ссылаются навигация, CTA или скрипт подсветки разделов; `#demo` — блок с существующими данными демо-входа.
- Удалить большую форму заявки вместе с обработчиком mailto-отправки; запрос доступа оставить компактными ссылками на email и Telegram.

- [x] **Шаг 1: заменить текст и разметку страницы по согласованной иерархии.** Первый экран: заголовок о контроле платежей и договоров, короткое пояснение, основная кнопка «Попробовать демо» (`#demo`), вторичная ссылка «Как это работает» (`#how`) и продуктовый дашборд-превью. Затем короткие результаты по просрочкам/оплатам, срокам договоров и доходам по объектам; сценарий «объект → договор → контроль платежей»; компактный фрагмент договора и платежа; блок `#demo` с текущими публичными данными демо-входа и кнопкой `/login`; короткий FAQ и контактные ссылки на email и Telegram. Заменить большую форму заявки этими компактными контактами. Сохранить ссылки на оферту, конфиденциальность, условия и статус.
- [x] **Шаг 2: встроить два превью продукта.** Первый экран должен опираться на структуру `CommandHeader`, `AttentionFeed`, `PropertiesOverview` и `AnalyticsWidget`; нижний фрагмент — показать связь договора с платежом. Пометить оба примера как демонстрационные и не вносить персональные данные или вымышленные метрики.
- [x] **Шаг 3: заменить CSS на компактную светлую композицию с зелёным акцентом.** Первый экран не должен занимать обязательную полную высоту viewport; блоки должны сканироваться как единая страница. На узком экране выстроить текст, CTA и превью в этом порядке. Сохранить видимый фокус, контраст кнопок и ссылок; учитывать `prefers-reduced-motion`.
- [x] **Шаг 4: упростить inline JavaScript под новую разметку.** Оставить плавный переход по существующим внутренним ссылкам и подсветку доступных секций. Удалить обработчик mailto-формы и связанные с ним константы. Не создавать ошибок, если необязательный элемент отсутствует.
- [x] **Шаг 5: проверить встроенные ссылки и сборку.** Проверить, что все `href="#…"` разрешаются в существующие IDs, внешние ссылки открываются безопасно, а `cd frontend && npm run build` завершается кодом `0` и копирует страницу в `frontend/dist/landing.html`. Попытаться снять desktop- и mobile-снимки; если headless-браузер не запускается в окружении, зафиксировать ограничение в ledger.

## Самопроверка плана

- Все блоки и визуальные ограничения дизайн-документа покрыты задачей 1.
- Форма и связанный с ней JavaScript рассматриваются вместе, чтобы не оставить ошибку обработчика.
- Новые зависимости, API, React-маршруты, analytics и backend-сбор заявок вне объёма.
- Проверка выполняется на статической странице и сборке; отдельные тесты в проект не добавляются.
